# Оглядач бази

Статичний інструмент для розбору JSON-збереження акаунта Clash of Clans.
Вставляєш дамп — бачиш, що на якому рівні, що відстає від стелі поточної
ратуші, скільки коштує все добудувати, що зараз у прокачці й що змінилося
з минулого разу.

Один файл, без збірки, без залежностей.

## Запустити локально

Відкрий `index.html` у браузері. Усе.

Якщо відкривати як `file://`, локальна тека `data/` браузеру недоступна —
інструмент тихо перемикається на пряме джерело ClashKing. Щоб працювала
локальна копія (і кеш), віддавай теку будь-яким статичним сервером:

```bash
python -m http.server 8765
```

## Захостити на GitHub Pages

1. Створи репозиторій і заштовхай туди цю теку:

   ```bash
   git init
   git add .
   git commit -m "оглядач бази"
   git branch -M main
   git remote add origin git@github.com:<твій-нік>/<репо>.git
   git push -u origin main
   ```

2. Settings → Pages → Source: **Deploy from a branch**, гілка `main`, тека `/ (root)`.
3. За хвилину сайт буде на `https://<твій-нік>.github.io/<репо>/`.

Нічого більше не потрібно: Jekyll не заважає, бо в проєкті немає тек із
підкресленням. `index.html` віддається як є.

## Що вміє

| Вкладка | Про що |
|---|---|
| Що прокачати | усе, що нижче стелі: вартість, час, суми по ресурсах; supercharge і злиття будівель для пізньої гри; експорт у CSV |
| Головне село | будівлі, пастки й помічники стрічками рівнів |
| Builder Base | будівлі й пастки другого села; аванпост О.Т.Т.О. поруч із домом будівельника |
| Армія · Герої · Спорядження | рівні проти стель; бюджет руди по героях |
| Прогрес | порівняння з попереднім знімком: що виросло і скільки це коштувало |
| У роботі | таймери з дампу й перерахунок «скільки лишилось зараз» |
| Діагностика | версія довідника, розділи дампу, ключі, яких інструмент не читає, невпізнані ID |

Фільтри (пошук, «тільки те, що відстає», «без стін», село) працюють
наскрізно, вкладка тримається в адресі (`#plan`, `#bb` …), таблиці
сортуються кліком по заголовку, на вузькому екрані стають картками.

## Що зберігається в браузері

Нічого нікуди не надсилається — усе лежить локально.

| Що | Де | Навіщо |
|---|---|---|
| дамп | `sessionStorage` | пережити F5; після закриття вкладки зникає |
| дамп (якщо ввімкнути «пам'ятати між сеансами») | `localStorage` | не вставляти щоразу |
| довідник | `localStorage`, ключ із версією | другий візит не тягне мережу взагалі |
| знімки бази | `localStorage`, до 12 на тег | вкладка «Прогрес» |
| вибрана тема й фільтри | `localStorage` / `sessionStorage` | дрібниці UI |

За замовчуванням дамп живе лише до закриття вкладки: у ньому є тег акаунта.

## Довідник рівнів

`_id` у дампі — це глобальний ID з ігрових таблиць, однаковий для всіх гравців.
Назви, стелі, вартість і час беруться з
[ClashKingInc/ClashKingAssets](https://github.com/ClashKingInc/ClashKingAssets) —
відкритого дзеркала ігрових даних.

Сайт вантажить **один файл** `data/ref.min.json` — це ті самі таблиці, з яких
викинуто все зайве (описи, TID, бойова статистика): ~590 КБ, близько 35 КБ
у gzip замість 1.6 МБ у п'ятнадцяти запитах. Порядок джерел:

1. `data/ref.min.json` — бандл, звірений із `data/meta.json` і кешований у браузері
2. `data/*.json` — окремі таблиці, як було раніше
3. `raw.githubusercontent.com/ClashKingInc/…` — напряму

Статус-рядок згори завжди каже, звідки прийшли дані, яка в них версія та
наскільки вони свіжі (зелений — молодші за два тижні, жовтий — за два місяці).

## Автооновлення довідника

`.github/workflows/refresh-data.yml` щодня о 04:00 UTC тягне таблиці в
`.staging/`, проганяє `tools/build_ref.py` і комітить **лише якщо дані
справді змінилися**. Запустити вручну можна з вкладки Actions.

`tools/build_ref.py` дорогою перевіряє дані: обов'язкові файли на місці,
ID унікальні, якірні сутності присутні, стеля ратуші не впала з минулого
разу. Якщо upstream зламався — скрипт падає, і бита копія не потрапляє в
репозиторій. Той самий скрипт можна ганяти руками:

```bash
python tools/build_ref.py --src data --out data --prev data/meta.json
```

**Ліцензія даних:** ClashKing під GNU GPL v3, походження зафіксовано в
`data/SOURCE.md` і `data/meta.json`. Не видаляй їх.

## Стелі рівнів

Максимум рахується не лише за ратушею. У даних кожен рівень має свої вимоги,
і всі вони враховані:

| Обмеження | Звідки береться рівень |
|---|---|
| `required_townhall` | Town Hall (`1000001`), для Builder Base — Builder Hall (`1000034`) |
| `required_lab_level` | Laboratory (`1000007`), Star Laboratory (`1000046`) |
| `required_blacksmith_level` | Blacksmith (`1000070`) |
| `required_hero_tavern_level` | Hero Hall (`1000071`) |
| `required_pet_house_level` | Pet House (`1000068`) |

Тому герої впираються в зал героїв, а не в ратушу, і підняття Hero Hall
одразу зсуває їхні стелі. Селектори згори дають подивитися, що відкриється
на наступному рівні залу; їхні межі беруться з довідника, тож нова ратуша
з'являється там сама, щойно приїдуть дані.

## Чому Builder Base — один список

У грі Builder Base — дві бази, але інвентар будівель **один**: кількості в
дампі рівно збігаються з тим, що відкриває поточний Builder Hall (перевірено
по всіх тридцяти типах будівель), а хто стоїть на другому етапі — вирішує
розстановка. Координат у дампі немає: записи згорнуті в пари
«рівень × кількість».

Тобто поділ на етапи з цього файлу не дістати. Ділити його «приблизно навпіл»
означало б видавати власне припущення за дані, тож вкладка показує Builder
Base цілком, одним списком. Аванпост О.Т.Т.О. стоїть у ньому поруч із домом
будівельника — видно і його рівень, і наскільки він відстає від стелі.

## Особливості формату дампу

Те, на чому ламається наївний парсер:

- ключ запису — пара `(data, lvl)`, а не `data`: один ID зустрічається кілька
  разів із різними рівнями
- трапляється ключ `dat` замість `data` — інструмент це ловить і показує
  попередженням, а не з'їдає запис мовчки; при цьому таймер чи кулдаун за ID
  не приймається, ID перевіряється за відомими префіксами
- записи зі станом (`timer`, `gear_up`, `weapon`) ідуть без `cnt`
- `1000097` має вкладену структуру `types → modules`
- `boosts` — об'єкт, решта колекцій — масиви
- ціни спорядження — це об'єкт по видах руди, а не число
- розділи, яких інструмент не знає, не зникають: масиви з ID підхоплюються
  автоматично, решта перелічена в «Діагностиці»
